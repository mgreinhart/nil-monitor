## 1. Critical issues

### 1.1 Admin CORS split is defeated by the Pages proxy — **critical**

**Where:** `functions/api/[[path]].js:14-16`

```js
const newResp = new Response(resp.body, resp);
newResp.headers.set("Access-Control-Allow-Origin", "*");
return newResp;
```

The Pages Function unconditionally sets `Access-Control-Allow-Origin: *` on every response it proxies. The worker goes to explicit trouble in `api.js` to give admin endpoints an `ADMIN_CORS` that *omits* this header (status doc: "Admin endpoints use no `Access-Control-Allow-Origin` header"). That defense-in-depth layer is erased by the proxy — `/api/admin`, `/api/trigger`, and `/api/admin/hide-headline` are reachable cross-origin via `nilmonitor.com` with `*` CORS.

**Why it matters:** HttpOnly cookies + SameSite=Strict still protect most of the attack surface (a third-party site can't force the browser to send the `admin_token` cookie on a cross-origin call). But the intent of the split-CORS design is gone, and any future mistake in the cookie policy has no second line of defense. The audit decision (#14 in the status doc) says the CORS split is "defense-in-depth alongside SameSite=Strict cookies." In practice there's no defense-in-depth; there's just SameSite.

**Fix direction:** Either (a) detect admin paths in the Pages proxy and skip the `Access-Control-Allow-Origin` header for them, or (b) stop claiming the CORS split is a defense layer and rely on cookies + csrf-same-origin. (a) is safer.

**Effort:** 1 session.

### 1.2 Three briefing gaps in the last 5 weeks went unalerted — **critical**

**Where:** Analyzed from the sitemap at `https://nilmonitor.com/sitemap.xml`

Sitemap dates vs. expected schedule (weekdays + Sundays, per `ai-pipeline.js`):

| Date | Day | Expected? | Present? |
|------|-----|-----------|----------|
| 2026-04-04 | Fri | yes | **missing** |
| 2026-04-05 | Sun | yes (PM) | **missing** |
| 2026-04-12 | Sun | yes (PM) | **missing** |
| 2026-04-18 | Sat | no | absent — correct |

Saturdays and missing Sundays-before-switch aside, three expected-but-absent briefings in ~5 weeks is ~10% miss rate. The pipeline has three fallback layers (primary cron, backup cron 1h later, and `ensureTodaysBriefing` on every fetcher tick), and none caught these. Possible causes I couldn't rule out from code alone:
- Cloudflare cron had an extended outage (plausible on free tier)
- `ensureTodaysBriefing` was short-circuited by a stuck `status='started'` row that outlived its 30-minute timeout window (the cleanup runs at the *start* of a new pipeline attempt, so if no new attempts fire, the lock sits forever — Cloudflare-outage scenarios)
- Anthropic API outage long enough that the single retry in `generateBriefing` (2 min wait) exhausted

**Why it matters:** The whole product thesis is "the first screen for athletic directors — did anything change overnight?" Missed briefings undermine that premise silently. A regular ADU reader who opens the dashboard Friday morning 4/4 sees Thursday's brief marked "Latest available," and if they don't read the fine print, they think they're caught up.

**Fix direction:** Add a health check that surfaces briefing gaps. Options:
- A weekly cron that counts briefings for the previous 7 expected-days and writes a flag table if any are missing, surfaced in the admin dashboard.
- A webhook/email alert from `ensureTodaysBriefing` when it detects a missed window (it already has the logic — just needs an out-of-band notification).
- Show "Last 7 days had N/M briefings" in the admin banner.

Additionally: the stuck-lock failure mode in `ensureTodaysBriefing` deserves investigation. The cleanup at pipeline start won't fire if no pipeline starts. Consider moving the stale-run cleanup into `ensureTodaysBriefing` itself so a stuck lock doesn't block recovery attempts.

**Effort:** 1 session for alerting; investigation of the root cause could be a few sessions if Cloudflare logs are needed.

## 2. Quality issues

### 2.1 Bing News fetcher produces ~50 briefing-invisible headlines per cycle — **high**

**Where:** `workers/fetch-bing-news.js:146`, `workers/rss-parser.js:17`, `workers/ai-pipeline.js:373`

The RSS parser extracts source attribution from `<source>` child elements:
```js
sourceName: extractText(block, 'source'),
```
Google News RSS items include `<source url="…">Outlet Name</source>`. Bing News RSS does **not** — the outlet is in the description/title suffix instead. So every Bing item falls back to the literal string `"Bing News"` in `fetch-bing-news.js:146`:
```js
const source = item.sourceName || 'Bing News';
```

In the latest 200 headlines, **46 of 200 (23%)** have source literally `"Bing News"`. That hits the aggregator-drop filter in the briefing generator:
```js
const AGGREGATOR_RE = /^(msn|bing|bing news|yahoo|yahoo news|aol|google news|...)$/i;
```

Net effect: the Bing fetcher runs 58 queries per cycle (`fetch-bing-news.js:17-96`), up to 30 times/day, and every headline it produces is **guaranteed** not to appear in a briefing. It contributes to the frontend headlines feed (23% of which is labeled "Bing News" with no real outlet attribution), which is also user-visible noise.

The Bing fetcher was added for "different index than Google News — surfaces different articles" (file header). That's still true in principle, but the pipeline as currently configured can't act on it.

**Why it matters:**
- Wasted CPU — 58 HTTP requests every 10-minute cycle, plus dedup cache lookups, for output the briefing rejects
- Noise in the frontend headlines feed — 23% of headlines with no publisher attribution
- Cost contributor to the "why is the feed mostly irrelevant" problem (§2.2)

**Fix direction:** Three options, pick one:
1. **Extract the real source from Bing** — Bing embeds the outlet in the `<description>` as "Outlet Name · Time ago" or in title suffix "Headline - Outlet". Parse it; set `source` accordingly. The aggregator drop stops catching them because the source is now real.
2. **Remove the Bing fetcher entirely** — the Google News queries overlap heavily (both indices cover the same English web). You're paying CPU + quota for near-zero marginal briefing signal.
3. **Tag Bing-sourced headlines with an internal flag** (`is_aggregator`) and have the aggregator-drop check that flag rather than a string match. Decoupling the logic would make future changes cleaner.

Option 1 gives you back a free coverage lane. Option 2 reduces complexity. Either is a clear win.

**Effort:** 1 session.

### 2.2 ~56% of frontend headlines are individual-athlete transfer noise — **high**

**Data:** Latest 200 headlines via `/api/headlines?limit=200`:
- Roster / Portal: **113** (56.5%)
- Business / Finance: 40 (20%)
- NCAA Governance: 13 (6.5%)
- Litigation: 10 (5%)
- Legislation: 9 (4.5%)
- CSC / Enforcement: 7 (3.5%)
- Revenue Sharing: 6 (3%)
- Null (awaiting tag): 2

Sampling the Roster / Portal bucket confirms the content is almost entirely what the briefing prompt explicitly excludes ("Individual player transfers or portal entries"):

> "Why UCLA Is Missing on Top Transfer Portal Talent"
> "Wisconsin basketball guard withdraws name from NCAA transfer portal"
> "Michigan basketball adds another SEC big man from transfer portal"
> "Oregon Lands 4-Star Alabama Forward in Transfer Portal"

The relevance gate in `fetcher-utils.js` lets "transfer portal" through as a positive signal, which is correct in principle — real portal *policy* stories use the phrase — but lacks any downstream gate to distinguish policy signal from roster gossip. The AI tagger correctly categorizes these as Roster / Portal (the taxonomy admits "Transfer portal windows, roster management rules, eligibility disputes, waiver decisions, scholarship limits"), but then they dominate the dashboard.

The briefing avoids them, but the headlines feed doesn't. From an AD's perspective, the /news view is 56% operationally useless.

**Why it matters:** The product's pitch is *regulatory intelligence*, not a sports-wire. Users opening the dashboard and seeing "Oregon Lands 4-Star Forward in Transfer Portal" in the primary feed learn that this isn't what they thought it was. It's also the lead category in the category-pill picker, further normalizing it.

**Fix direction:** Several non-exclusive options:
1. **Add a second Roster / Portal sub-classification** in the tagging prompt — split into `Roster / Portal — Policy` (rule changes, window policy, eligibility waivers) vs `Roster / Portal — Individual` (player transfers). Only show Policy in the default headlines feed. Individual hides behind a filter.
2. **Tighten the portal-noise filter in `fetcher-utils.js`** — `isPortalNoise` already exists but is narrow. Expand to catch the "Player X [verb] portal" pattern without a policy anchor. Risk: false positives on policy stories that mention a player as example.
3. **Move Roster / Portal behind a click** on the default `/api/headlines` response — expose a param like `excludeCat=Roster / Portal` and use it by default from the frontend.

Option 1 is the cleanest long-term. Option 3 is a one-hour fix.

**Effort:** Option 3 = 1 session. Option 1 = a few sessions (prompt tuning + tag migration).

### 2.3 `/api/cases` ships 184KB to every page load — **high**

**Where:** `workers/api.js:568-598`, `src/App.jsx:803-804`

Measured size of `https://nilmonitor.com/api/cases`: **184,360 bytes**. Frontend fetches this unconditionally on page load, parses 97 case objects, and then uses only:
- Top 5 upcoming dates (by `soonest` from `upcoming_dates` JSON)
- Recently-updated cases (30-day window, collapsed to "recentActivity")
- Total count for a header metric

The rest — every case's full `description`, `status_summary`, `last_event_text`, `upcoming_dates` JSON blob — is shipped but not rendered unless a user clicks a specific case card to expand. On mobile on 4G this is a real slowdown. Cold fetch took ~350ms in my measurement, and on worse networks the parse+copy cost to React state compounds.

**Why it matters:** 184KB over the wire for data that gets projected down to ~10KB of rendered output is structurally wasteful. The response is ~1.9KB per case × 97 cases. For the Courtroom panel's default view, you could ship ~10 cases × ~300 bytes each = ~3KB.

**Fix direction:** Add endpoint variants:
- `/api/cases/summary` — returns just `name`, `case_group`, `last_event_date`, `soonest_date`, `soonest_text` (computed server-side) for the list view
- `/api/cases/:id` already exists — fetch full details lazily on expand

**Effort:** 1 session.

### 2.4 7 render-blocking third-party font stylesheets — **high**

**Where:** `index.html:71-77`

```html
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@fontsource/geist-sans/index.css" />
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@fontsource/geist-sans/500.css" />
... (×5 more)
```

Seven separate `<link rel="stylesheet">` requests to jsdelivr, all render-blocking, all cross-origin. Measured first-byte time to nilmonitor.com root: **289ms**, total: **290ms** — fast origin, but then browser issues 7 parallel font-CSS requests before first paint can complete.

Each of those CSS files then @import font WOFF2s from the same CDN. That's ~14 serialized resources (7 CSS + at least 7 font binaries) gating Largest Contentful Paint.

**Why it matters:** LCP is probably 1.5–3s on typical connections, not the sub-second the origin itself could deliver. Fonts are the bottleneck. Also: jsdelivr is a dependency you don't control — if it has an outage, the site renders in fallback fonts (or with FOIT, depending on CSS).

**Fix direction:**
- Consolidate to two `<link>`s — Geist Sans variable font (one file covers all weights) and Geist Mono variable font.
- Consider self-hosting via `/public/fonts/` and serving off Cloudflare Pages (same origin, same CDN, one less domain in the critical path).
- Add `font-display: swap` in the CSS (most @fontsource builds already include it; worth confirming).

**Effort:** 1 session.

### 2.6 `fetcher_errors` table does a DELETE-full-scan on every error insert — **medium**

**Where:** `workers/fetcher-utils.js:168-173`

```js
await db.prepare(`INSERT INTO fetcher_errors (...) VALUES (?, ?)`).bind(fetcherName, msg).run();
await db.prepare(
  `DELETE FROM fetcher_errors WHERE id NOT IN (SELECT id FROM fetcher_errors ORDER BY id DESC LIMIT 100)`
).run();
```

The `DELETE` has a subquery that must sort the entire table by id DESC, take the top 100, then the outer query scans the whole table checking NOT IN. With an index on `id` this is mostly cheap, but on D1 it's still two statements per error event and scales linearly with table size until the cap is reached.

**Why it matters:** Currently a minor inefficiency. Noticeable if fetchers start erroring in bursts (e.g., an API outage causes all 11 fetchers to fail twice per cycle). Also does a DELETE write after every error, which is rarer-on than reads but still counts against D1 write quota.

**Fix direction:** Two options:
1. Run the trim opportunistically (e.g., only when `random() < 0.1`) rather than after every insert.
2. Move the trim to a daily cron pass and accept the table growing to ~1K rows between trims.

**Effort:** Under 1 session.

### 2.7 Google News redirect URLs stored verbatim; briefings link through Google — **medium**

**Where:** `workers/fetch-google-news.js:144`, visible in every `/api/briefing` response

The Google News RSS item `<link>` is a Google-side tracking/redirect URL (`news.google.com/rss/articles/CBMiv…?oc=5`). It's stored as-is in `headlines.url` and surfaced in briefings. All 4 items in today's briefing link to Google News redirect URLs:

```
https://news.google.com/rss/articles/CBMivAFBV…?oc=5
```

Every click = 2-hop redirect (nilmonitor.com → news.google.com → publisher), and Google gets a tracking event each time.

**Why it matters:** Minor UX degradation. More importantly for the AI pipeline, dedup keys on URL, and these opaque base64 URLs dedup cleanly across sources — but you lose any visibility into "is this the NYT version or the SI version" at the URL level, and clicked-through analytics (if you add them later) will look like everyone reads news.google.com.

**Fix direction:** At insert time, follow the Google redirect with a HEAD request and store the final publisher URL. Caution: Google rate-limits this aggressively, so batch it carefully or do it lazily (first time each URL is actually rendered). Also note: the redirect page is no longer a simple 302 for many Google News items — it's a JS page that performs the jump, so HEAD might not resolve. Needs research.

**Effort:** A few sessions (research + retry logic + caching).

## 3. Optimization opportunities

### 3.1 Prompt caching is unused; the briefing prompt is ~2,500 tokens re-sent every run — **high value**

**Where:** `workers/ai-pipeline.js:402-586` (briefing system prompt), `:123-172` (tagging system prompt)

The briefing system prompt is ~550 lines, roughly 2,500–3,000 input tokens. It's identical across every run. The tagging system prompt is ~700 tokens, also identical across runs.

Anthropic's API supports prompt caching with explicit `cache_control` breakpoints: cached prefix tokens cost ~10% of the base input rate and have a 5-minute TTL (or 1 hour on extended cache). Daily AI runs: 2 briefings + ~15 tagging batches = ~17 calls/day. If every call re-sends the full system prompt, you're paying full rate for ~51K tokens/day that could be cached.

Very rough cost comparison (Sonnet 4.5 rates: $3/MTok input, $15/MTok output):
- Current: ~17 calls × 2500 input = 42,500 input tokens/day for prompts alone → $0.13/day
- With cache: first call $0.13, subsequent calls in the same cache window at $0.013 → realistic ~$0.02/day saved
- Over a year: $36–50 saved on prompts alone

The dollar impact is modest. The real value is latency (cached prefix is faster) and discipline — prompt caching forces you to keep the system prompt static, which pushes variable content (headline list, deadlines) into the user message where it belongs.

**Fix direction:** Add `cache_control: { type: 'ephemeral' }` on the last content block of the system prompt. Anthropic docs walk through this. `callClaude` in `ai-pipeline.js` would take a `cachedSystem: true` flag.

**Effort:** Under 1 session.

### 3.2 Tagging could drop to Haiku 4.5 for ~10× cost reduction — **high value**

**Where:** `workers/ai-pipeline.js:7`

```js
const MODEL = 'claude-sonnet-4-5-20250929';
```

Tagging is a well-defined categorical classification — 9 categories, clear examples in the prompt, sub-category only for CSC. It's a recognizable pattern that Haiku 4.5 should handle well. Briefing writing is the task that genuinely needs Sonnet's reasoning depth.

Sonnet 4.5 vs Haiku 4.5 pricing (approximate): Sonnet $3/$15 per MTok input/output; Haiku $1/$5 per MTok. Tagging runs ~15 batches of 50 headlines/day = ~750 headlines/day through Sonnet. Each batch is roughly 2K input + 1K output tokens. Daily tag cost on Sonnet is ~$0.60–$0.80. On Haiku it'd be ~$0.20. $150–200 saved per year, plus faster tag runs (less CPU time eaten by waiting).

The status doc says pipeline cost is ~$1–3/day. If tagging is ~$0.70 of that and briefings are the rest, the tagging swap is ~25% of the daily cost for no expected quality loss.

**Why I'm confident this is safe:** The Off-Topic Guardrails section of the tag prompt reads like it was written to make a less-smart model not screw up simple cases. Haiku 4.5 should follow those rules fine. Real risk: CSC sub-category inference (`Guidance / Investigation / Enforcement / Personnel / Rule Clarification`). Lower-volume; could keep Sonnet for that batch if needed.

**Fix direction:** Pilot with a parallel `MODEL_TAG = 'claude-haiku-4-5-20251001'`. Run tagging via Haiku; keep briefings on Sonnet. Sample the output for a week and compare to a Sonnet control run. If accuracy holds, switch.

**Effort:** 1 session to pilot, a few sessions to evaluate before committing.

### 3.3 Briefing system prompt has accumulated contradictions — **medium value**

**Where:** `workers/ai-pipeline.js:402-586`

The prompt now carries ~25 named rules (PRIORITY HIERARCHY, CONSOLIDATION RULE, PATTERN CLAIMS RULE, HEARING DETECTION, SOURCE DIVERSITY CHECK, STALENESS CHECK, POLITICAL COMMENTARY RECENCY RULE, CALENDAR DATES ARE NOT NEWS, STRICT FORMAT RULES, plus six separate PRIORITY sections and ten-ish other guidance blocks). Some friction:

- **LEAD STORY RULE** says "identify the single most consequential story" and lead with it.
- **PRESIDENTIAL / EXECUTIVE BRANCH PRIORITY** says "ALWAYS the lead story when they occur."
- **CSC / ENFORCEMENT PRIORITY** says "ALWAYS high-priority items."
- **REVENUE-SHARING CAP MECHANICS PRIORITY** is "MUST-INCLUDE" and "takes priority over any repeated story and over routine enforcement."

When two of these fire at once (likely on a busy news day), the model has to pick, and the prompt doesn't tell it which priority beats which.

**PRIORITY HIERARCHY FOR STORY SELECTION** then lists a 6-step hierarchy (state legislative action → federal hearings → institutional financial restructuring → new enforcement guidance → federal bill introductions → political commentary). This contradicts or overlaps with most of the ALWAYS-PRIORITY blocks above.

- **MUST-INCLUDE WHEN AVAILABLE** lists university-president statements, AD financial-strategy disclosures, academic legal scholarship, NCAA licensing actions. These aren't in the priority hierarchy.
- **LOW-PRIORITY** enumerates things to skip but overlaps with EXCLUSION RULE — PERSONNEL HIRES.

Token cost of the prompt (~2,500 input) is modest; the real cost is **decision drift** — the model is holding multiple competing "always" rules and quietly picking whichever is most salient in the last 500 tokens of context.

**Why it matters:** Prompt drift is likely the largest source of briefing quality variance week-to-week. Every new rule you added over the last month solves a specific failure mode but accumulates next to every prior rule without pruning.

**Fix direction:** Refactor to a clear three-layer prompt:
1. **Identity & format** (voice, output shape, source fidelity) — static.
2. **Priority ladder** (one ordered list, each rule with a condition). Move all the ALWAYS-PRIORITY content into slots on this list.
3. **Exclusions** (one merged block — calendar dates, individual personnel, political-commentary-recency, low-priority, pattern claims). Today these are scattered.

Side benefit: once flat, the priority ladder can be tested by giving Claude an "evaluate which rule applied to each briefing item" pass. That's a quality metric you don't have today.

**Effort:** A few sessions (refactor + validation).

### 3.4 Missing indexes on common query paths — **medium value**

**Where:** `schema.sql:52-65`, various query sites

The `headlines` table has auto-index on `id` and UNIQUE index on `url`. The following columns are in WHERE/ORDER BY clauses without indexes:

| Query (representative) | Columns without index | Source |
|------------------------|----------------------|--------|
| `WHERE fetched_at >= datetime('now','-24 hours')` | `fetched_at` | `api.js:195` |
| `WHERE published_at >= date('now','-3 days')` | `published_at` | `fetcher-utils.js:92` |
| `WHERE category = ? AND ... ORDER BY published_at DESC` | `category`, `published_at` | `api.js:630` |
| `WHERE category IS NOT NULL AND ... ORDER BY CASE severity WHEN ...` | `category`, `severity`, `published_at` | `ai-pipeline.js:349` |
| `WHERE fetched_at > ?` | `fetched_at` | `ai-pipeline.js:108` |
| `WHERE category IS NULL OR severity IS NULL` | `category`, `severity` | `api.js:201` |

Dedup cache pre-load alone scans the table filtered by `published_at >= date('now','-3 days')` on every cron invocation. Without an index, that's a full table scan, and the table is growing ~40 rows/day with id auto-increment at ~925/day (most rejected on URL UNIQUE, still burned IDs).

**Why it matters:** D1 free tier limits rows-read. I don't have direct access to check usage, but the admin dashboard's parallel queries fan out to 15 queries per load, most unindexed. Every cron tick runs dedup cache load + fetcher error record. Scales unfavorably.

**Fix direction:** Add composite indexes:
- `CREATE INDEX idx_headlines_published ON headlines(published_at DESC);`
- `CREATE INDEX idx_headlines_category_published ON headlines(category, published_at DESC);`
- `CREATE INDEX idx_headlines_fetched ON headlines(fetched_at DESC);`

Test impact with `EXPLAIN QUERY PLAN` via `wrangler d1 execute`.

**Effort:** 1 session (indexes + verification).

### 3.5 No retention policy on `headlines`, `pipeline_runs`, `csc_activity` — **medium value**

None of these tables get cleaned up. Headlines grow ~40/day, pipeline_runs ~4/day, csc_activity a few/week. Over a year: ~15K / 1,460 / ~500 rows respectively. D1 free tier is 5GB — nowhere near exhausted, but the dedup cache's 3-day scan will stay cheap longer if the table is shorter, and admin dashboard queries ("total headlines") are more meaningful when they reflect recent reality.

**Fix direction:** Add a weekly cron task or trigger phase that deletes headlines older than N days (180?) except those referenced by a briefing `source_index`. Trickier than it sounds — you'd need to preserve "headlines referenced by published briefings" to keep historical briefing links working. Simpler alternative: archive to a `headlines_archive` table monthly.

**Effort:** A few sessions (schema design matters more than the code).

### 3.6 Bundle size: 376KB raw / 116KB gzipped — **low value**

`react-simple-maps` + `us-atlas` topology are the heavy hitters. The state map is one screen of the app; it's loaded on the initial bundle even if the user never scrolls to it. Code-splitting it via `React.lazy` would shave ~100KB off first-load JS.

**Why it matters less than it sounds:** The site loads fast enough (290ms first byte) that the bundle isn't the bottleneck right now; the fonts (§2.4) are. Fix fonts first, then revisit this.

### 4.2 Fetcher query lists embedded inline — **mild debt**

`fetch-google-news.js` has 88 query strings in an inline `const QUERIES = [...]`. Bing has 58 more. Editing them requires scrolling a 200-line file. There's no tooling for catching overlap between them, or noticing that SCORE Act is queried 3 ways across both fetchers.

Two related observations:
- Some queries are clearly redundant (`'"SCORE Act" college sports'` in Google News, `'"SCORE Act" OR "SAFE Act" college sports'` in Bing, `'"SCORE Act" revision OR markup OR "floor vote"'` in Bing)
- The `fetch-google-news.js` comment says "Trimmed from 105 to 76" — but it's been re-grown to 88 without updating the note. Every refactor pass should end with updating that count (the status doc and audit now agree, but the source file lies).

**Fix direction:** Low priority. Consider moving queries to `workers/queries.json` so they can be edited without touching JS. Lets you do overlap analysis (`jq`-style) without parsing code.

**Effort:** Under 1 session; defer unless you start making frequent query edits.

## 5. Strategic observations

### 5.1 The ingestion/curation ratio is inverted

You're fetching from 190 sources (88 Google queries + 58 Bing + 18 NewsData + 23 publications + 3 NCAA) and then applying increasingly strict filters to produce 4 briefing items per cycle. That's ~190:1 signal-to-surface. The curation logic has accumulated a lot of intelligence — aggregator drop, 5-briefing anti-repetition, political-commentary-recency, personnel exclusion, pattern-claim rule — and most of it is load-bearing because the input is so noisy.

An alternative shape: fewer high-signal sources, lighter curation. You'd lose the occasional long-tail story but the briefing wouldn't have to fight so hard for every item. Concretely:
- Bing News (§2.1) is currently 0-value for briefings; drop it.
- NewsData.io is 18 queries with a 200-credit/day free tier. Is it adding stories Google News doesn't already have? Worth sampling.
- The 88 Google News queries have genuine overlap; some are experiments that never got cleaned up ("Teamworks college sports" is a single-vendor query that competes with the broader "athletic department technology" query).

You're paying for breadth, complexity, and CPU to run a briefing system that then has to be brilliant at rejection. Either commit to being a broad-index provider (and fix the "56% portal noise" UX) or narrow to the 20-30 sources that actually drive briefings.

### 5.2 The Courtroom / Cases section is the product's real differentiator

Of everything I looked at, CSLT integration is the strongest asset. 97 tracked cases, court metadata, upcoming hearing dates, update streams. This is what a subscription sports-business tracker (SBJ, Sportico) doesn't give you for free, and it's operationally actionable for ADs and compliance officers. It's also getting less pixel-real-estate than the MOCK-fallback headlines feed.

Specifically:
- Upcoming key dates are a scroll down, not above the fold.
- "Recent activity" is hidden inside an expandable.
- The State NIL map (which is static data) gets more screen space than the live CSLT data.

Investing more here would differentiate the product. Examples: email alerts when a tracked case's upcoming date changes; cross-reference with briefings to surface "you mentioned this case three briefings ago, here's the new filing."

### 5.3 The PE Tracker pretends to be live data

10 manually seeded deals. Hasn't been updated since initial seeding (the status `created_at` is 2025/2026 static). Frontend displays it alongside live data with the same visual weight. No "last updated" indicator, no "curated by" attribution.

This is fine for now — PE deals in college athletics are infrequent enough that manual curation makes sense. But it's dishonest by omission. Either:
- Label it "Curated manually, last updated YYYY-MM" on the panel
- Build a simple admin UI (you already have hide/unhide infrastructure) to add deals on demand

### 5.4 State Legislation map is 2+ months stale

`nil-state-data.json` from "Troutman Pepper (Feb 2026)". We're in April. Blocked on LegiScan API key per status doc. The map displays as current data. Same honesty gap as PE Tracker.

### 5.5 Zero usage-level analytics

The only signal on whether anything here is used is Cloudflare Web Analytics pageviews — no clicks, no briefing-opens, no category-filter usage. You can't answer "do people expand the briefing?" or "which category pill gets clicked most?" or "are the hide/unhide admin tools actually being used?" (the sample I pulled showed 0 hidden headlines in the latest 200; admin curation infrastructure exists but might be dormant). This is a real strategic gap — all the briefing prompt refinement is being made blind to what users read.

Lightweight fix: a client-side `POST /api/analytics` with action names (`briefing_expanded`, `category_filtered`, `headline_clicked`). Sample them. Even 2 weeks of data would settle several open questions about where to invest.

### 5.6 What I'm investing in vs ignoring

**Invested in:** Briefing quality (25+ rules in the prompt, 5-briefing anti-repetition, aggregator drop). Pipeline reliability (backup slots, distributed lock, safety net). Source coverage (expanding queries, adding NCAA.org RSS, federal legislation coverage). Admin/curation tooling.

**Under-invested:** Frontend density (the live data asset is buried). Mobile experience (I didn't load the site on a phone but the inline styles have isMobile branches that feel like afterthoughts). User-level analytics. The Cases section's surface area. Cleaning up ingestion (Bing News's silent dead-weight is the tell — nobody was measuring whether it contributed).

**Outright ignoring:** Congress fetcher (never built despite key being set). Deadline extraction (referenced in schema, never implemented). CourtListener integration (fetcher runs, always skips — a function call doing nothing every 2 hours). LegiScan (waiting on key approval, no manual-update alternative shipped in the interim).

The pattern: backend pipeline refinement has had 30+ commits of investment while frontend/UX has had small tweaks. This is natural for a data-heavy product early on, but the user-facing surface is starting to lag the data layer.
